> scripts name the scratch folders they first ran from.

| Check | Result |
|---|---|
| A real node: BCHN v29.0.0 against libauth | **Same verdicts.** 179 transactions in standard mode, consensus mode and mined blocks, all with the same verdict. BCHN's op cost is libauth's plus the defined bodies, as the prover assumes. The lowest margin on BCHN is 5.88%. |

## 1. A real node

**The setup.**
- Docker image `mainnet/bitcoin-cash-node:v29.0.0` (build 89a591f7c), in regtest with the 2026 upgrade active. One node ran at public relay policy; one ran with `-acceptnonstdtxn=1`, to judge consensus and to mine blocks.
- A BCH pool was deployed and run with the project's own code, with 6 deposits finished.
- Withdrawals were built by the SDK and captured without being broadcast.

**Verdicts.** Every case of `tamper.ts`, `forge.ts` and `run-real-proof.ts` was rebuilt on the node's real coins. Each ran twice: beside the real pool, and beside a stand-in master, so that the verifier's own failure shows.
- That made 179 transactions: 12 accepted and 167 refused.
- libauth and BCHN agree on every one. They also agree on the opcode the first failing input stops at, in standard mode, in consensus mode and in mined blocks.
- Forged statements fail at the last comparison on BCHN too. A re-randomised proof is accepted.

**Op cost.** BCHN does not report op cost, so it was bracketed. An input's filler was shrunk until BCHN refused it with "VM cost limit exceeded".
- **Input 2** of the shipped code: 21 bisections on 19 statements, 3 of them real withdrawals from the pool. BCHN's boundary equals the model's every time.
  - BCHN − libauth ∈ (16,286, 16,323]. The prover adds 16,313 for the defined bodies.
- **Inputs 0 and 1** are accepted even with no filler, so they cannot be bracketed directly. A test variant made their budget bind with a balanced loop, and matched the model in all 198 bisections, 12 of them in mined blocks.
- Across 3,883 op-cost probes, the model's verdict never differed from BCHN's.

**Lowest margin on BCHN:**
- 5.917% on input 0 of an SDK-sized withdrawal;
- 5.881% with all three inputs at the 10,000-byte cap;
- 5.985% on the pool's own root.

**Changed as a result.** The prover's `sizeFills` now throws if a run it measures stopped early. That happens when a guard refuses it, when the brand source is not set, or when the budget runs out at the cap. Before, it returned fillers sized from a partial cost. The page was not affected, since it sets the brand.

**Not done:**
- the token pool;
- the hash-iteration limit;
- consensus-mode op cost beyond 4 statements.

## 2. The bytecode against the math

- **Identity.** The generator rebuilds the template byte for byte: 8,212 B, sha256 `37c8b9ec…`, and the same 69 B redeem.
- **Guards.** The exact condition each guard checks was derived from the bytecode: 199, 203 and 267 checks in roles 0, 1 and 2.
  - Each was compared with the guards table in the generator's README, and every one matches.
  - Nothing the code accepts is refused by the spec.
- **Functions.** A symbolic executor was written for the opcodes the verifier uses.
  - It was first validated against libauth: 51 of 51 verdicts and final stacks agree.
  - It expanded each function's outputs and guards to polynomials, and compared them with formulas taken from the README, `protocol.mjs` and `math.mjs`. That gave 219 proofs, with no failure, covering every function and the roles' wiring.
  - The loop's per-event step was checked by evaluation at 1,536 random points. Its degree is at most 63, so the error is at most 2^−248 per point. That makes it a randomized proof.
- **Tests.**
  - 167,325 runs of single functions against an independent BigInt reference, with boundary, non-canonical and wrong-length inputs: 0 mismatches.
  - Twenty one-byte mutations of the code were all caught.
  - The role programs matched `protocol.mjs`'s mirror at 5,119 checkpoints in 28 runs, 10 honest and 18 forged. Every forgery was refused at the guard it was designed to hit.
- **The assembler** was read line by line. Its `drop()` kept a wrong stack model when a pile of no items sat above the dropped item. No such case occurs in this build. It is fixed, and the code hash is unchanged.
- **Docs fixed.** Four passages of the generator's README still described the two-input build.
- **Limits:**
  - the loop step's proof is randomized;
  - the size and layout guards were derived with concrete lengths, not symbolically;
  - nobody has reviewed the executor independently;
  - the reference mirror and the code come from the same author, though the audit checked the math against noble separately;
  - the z = 0 refusal, and non-minimal inputs to BADD, DSTEP and BNDSTEP, were not exercised.
- **Found on the way.** bch-next's libauth is mainnet-pat's fork at `1cf4b43`, not the npm release that the audit called stock. The two gave the same verdicts throughout, and the same op cost on every input of the fixture withdrawal.

## 3. The trusted setup

- **Ethereum.** Tornado's 0.1, 1, 10 and 100 ETH instances all call the verifier at `0xce172ce1F20EC0B3728c9965470eaf994A03557A`. Three RPC endpoints agree.
  - The instances' operator is the zero address, so nobody can change it.
  - Its runtime holds our key's 28 numbers, and solc 0.5.17 with Tornado's settings rebuilds it byte for byte, apart from metadata.
  - A recent real withdrawal from each instance verifies under our key. With the fee or the recipient changed, it does not.
- **Circuit.** circom 0.0.35, with the pinned circomlib, compiles tornado-core's `withdraw.circom` to `withdraw.json` byte for byte, apart from file paths in assertion strings. That is tag v2.1, the same as the local checkout.
  - The result has 28,275 constraints and 6 public inputs.
  - It is also the v2.1 release asset and the ceremony's own `circuit.json`.
- **Ceremony.** These ran on the ceremony's own code, phase2-bn254 as of May 2020:
  - The initial parameters rebuild byte for byte from the circuit and the phase-1 file.
  - `MPCParameters::verify` passes on the final `tornado.params`: 1,114 of 1,114 contribution links hold. Three negative controls fail, as they should.
  - Four intermediate responses recovered from the archived transcript are exact prefixes of the final file, and each verifies on its own.
  - The key read from `tornado.params` equals ours. Its export equals tornado-core's `withdraw_verification_key.json` byte for byte.
  - The phase-1 file is well-formed: one (τ, α, β) explains every element.
- **What stays trusted.** Proofs are sound only if both of these hold:
  - **Phase 2:** at least one of the 1,114 contributions destroyed its secret. Nothing proves they were distinct people. About 1,060 browser contributions also trusted the ceremony page's code.
  - **Phase 1:** at least one of the 29 people behind Perpetual Powers of Tau contributions 1–30 destroyed their secret, **and** the phase-1 file really came from contribution 30 with Tornado's beacon.
    - That last link can no longer be checked, because the Powers of Tau files and the beacon value are offline.
    - If the file came from anywhere else, whoever made it can prove anything, whatever phase 2 did, because γ is the generator.
    - On that point the pools trust Tornado's 2020 team, as everyone who uses Tornado does.

A human audit of the verifier and of the contracts is still advised before mainnet funds; see `PRODUCTION.md`.
