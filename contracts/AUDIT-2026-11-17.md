# SolidPool bytecode audit, 2026-11-17

An AI review, not a human audit. A Claude agent on the Fable model read SolidPool's compiled
contracts and the shipped verifier template at commit `9ceafd7`, checked rules in libauth's 2026
VM, and changed nothing. Its report follows as written, except for the Files section at the end.

Since then:

- each factory's `create` refuses every other output of its category (`7da7067`), which closes
  finding 1 on chain. That change has had no audit of its own;
- the readers count a `PoolCreated` only where `create` writes it (`0d557ba`);
- `AUDIT.md` and `PRODUCTION.md` describe findings 2 to 5.

## Verdict

I found no way to take depositors' funds, forge a withdrawal, double-spend a note, or stop a pool for good in the shipped bytecode of BchPool, TokenPool, MimcHash or the verifier template. The rules the pools rely on are enforced at the opcode level and are enough for fund safety.

The factories have one real gap. A `create` call lets its caller mint forgeable `PoolCreated` records, and the project's readers accept them. That breaks "one pool per amount / per asset and amount" as listed, and "PoolCreated bound to a real creation", and it can permanently break token-pool creation through the page. No funds are at risk from it, because every pool the indexer lists is still a sound pool. Fix it before mainnet: the factories are not deployed yet, so both an on-chain and a reader fix are open.

Everything was checked in the project's libauth 2026 VM (standard and consensus modes), not on BCHN. Two forks of this agent did the verifier and factory slices; I re-ran the factory forgery myself and confirmed its bytecode basis by reading.

## Findings

### 1. High (list integrity and creation liveness, no funds): a creator can mint forged `PoolCreated` records

- **Where:** `BchPoolDeployer.json` `create`, the last own-category output loop before the final `2DROP 1`; `TokenPoolDeployer.json` fn `0x1a6a6669`, same loop. The opcodes are `… OVER OUTPUTBYTECODE <51> EQUAL NOT BOOLAND IF DUP 2 PICK SUB 2 3 WITHIN VERIFY ENDIF`.
- **Rule and why it fails:** an immutable NFT of the factory's category with a commitment must sit at master index + 2, the event slot. The loop exempts any output whose lock is exactly `0x51`, and the factories have no count of such outputs. The pools do have that count (the `BIN2NUM <0001> MOD <51>` helper, fn `0xa4` in BchPool), so the pools are not affected. I checked this: a forged record at `0x51` beside a pool `finish` or `withdraw` is refused in both pools.
- **Shapes accepted (VM-checked, both factories, script `_dp_forge.ts`):**
  - An honest creation plus one extra output `{lock 0x51, factory category, immutable, commitment = a well-formed PoolCreated naming any category}`.
  - A 164-byte transaction moving that NFT to the `PoolCreated` address. `factoryPools()` then lists the forged pool beside the real one.
  - A pool born through `Deploy<C>` with no factory in the transaction, the pre-minted NFT paid to the event address in its genesis. `genesisProblems()` returns `[]` and `factoryPools()` lists it. `Deploy<C>` does not check who calls it.
- **Impact:**
  - **Token factory:** anyone can do this at any time, by creating a pool of an asset they mint.
    - A forged record in an occupied slot makes `registryTree()` throw "That slot of the tree is taken" (checked).
    - A forged record in another slot should give a root mismatch (read, not run).
    - Either way the page's Create pool (`web/src/engine.ts:752`) and `scripts/deploy.ts` fail for every token pool until the readers are fixed.
    - The indexer can be made to list any number of extra pools for an asset and amount.
  - **BCH factory:** only inside one of the five possible creations, but one creation can mint many records. If the deployer leaves any amount unmade, whoever makes it can pre-mint duplicates of every amount.
  - **Funds:** safe. The indexer runs `genesisProblems` on each candidate, and `Deploy<C>` pins the whole genesis on chain, so a listed pool is always a sound one. The damage is split anonymity sets, a list that no longer means one pool per amount, and broken creation.
- **Fix:**
  - **On chain:** in both factory sources, refuse any output of `this.category` outside master index, +1 and +2, then confirm the loop in the compiled bytecode. Or fix SolidCash to keep `0x51` immutables in the census when the function emits no return record.
  - **Readers** (`web/src/factory.ts` `factoryPools`, `indexer/discover.ts` `scan`, `scripts/lib/genesis.ts` `namesThePool`): count a `PoolCreated` only in a transaction whose output i is the factory's minting NFT at the factory lock, with the event at i + 2; in `genesisProblems` also require the pool master at i + 3.

### 2. Low (liveness griefing): shared coins can be moved by anyone

- **Where:** verifier code role 2, where the per-pool brand check was removed; MimcHash's hash path.
- **Shape:** three verifier coins alone with any valid proof over a made-up root, recreated as they were (VM-checked, accepted). A hashing coin beside any input with a true hash (the project's own test).
- **Impact:** changes the coins' outpoints and spoils a withdrawal or deposit in flight that names them. It costs about 30 kB of fee per verifier move and 8 kB per hashing coin, against 510 B for the satoshi-coin move the docs already accept. It cannot block for good: anyone can pay fresh coins to either lock.
- **Fix:** none needed in bytecode. Document it beside the satoshi-coin griefing.

### 3. Low: the factory's state record can be respent in place by anyone

- **Where:** the record lock's flag-0 path (commitment, lock, category and value kept; no master needed).
- **Impact:** spoils a creation in flight. Same class as the pools' record move, but not documented for factories. By reading, not run.

### 4. Low: a verifier or hashing coin carrying a token is accepted and the token burned

- **Where:** verifier fn 4 and MimcHash require no token on the recreated output and say nothing of the input.
- **Shape:** the BCH withdrawal with a foreign token on the last verifier coin (VM-checked, accepted). Not run beside TokenPool's withdraw.
- **Impact:** none on a pool. `deposit` refuses such a transaction, and the client filters token coins out (`spendableCoins`).

### 5. Informational

- **Uncensused NFTs of a pool's own category.** Any pool call can mint an immutable NFT with an empty commitment, or one shaped like SolidCash's identity anchor (`SCID\x01 … master lock`), at any lock (VM-checked in both pools, `finish` and `withdraw`). Neither parses as an event or as state, and `history.ts` skips them, as documented. Mutable and minting extras, and any event-shaped record outside its slot, are refused.
- **Malleability the docs do not list.** Accepted in the VM: the state record unlocked with flag 4 instead of 1, return index −2 instead of −1, a 65th sibling in `withdraw`. Same class as the listed ones; the client keys on no txid.
- **Token withdrawal: the recipient coin's satoshis are free.** Only its lock, asset and amount are pinned. Whoever rebuilds a withdrawal can open it at dust (663 sat, consensus takes 600) and keep the difference, about 540 sat more than the fee slack the docs state.
- **Duplicate commitments are accepted.** A note deposited twice can be withdrawn once; the second deposit stays in the pool. The client always makes a new note.
- **`BN254.json` is not used by any coin.** Only `scripts/measure.ts` reads it. Its constant `P` is the BN254 scalar field r, not the base field, so it must never be taken for curve arithmetic.

## What holds in the pools (opcode-read, with VM checks where marked)

- **Dispatch.** The master redeem is `<category‖02> INPUTINDEX UTXOTOKENCATEGORY EQUALVERIFY <args> <code>`, and equals the artifact's `debug.bytecode`. The selector must be 4 bytes, and only the four public functions have 4-byte identifiers. `__construct` needs input 0 to spend `(own category, 0)`, which cannot happen once the category exists.
- **Value conservation.**
  - `deposit`: the satoshi-lock delta is exactly denomination + fees; output 2 ≥ 1,200 + notes × (denomination + fee) + finish fee; exactly one output at the satoshi lock.
  - `finish` and `withdraw`: sums over every satoshi-lock input and output, and the coin at input 2 loses at most the fee, or the fee plus the pinned transfer.
  - One satoshi more is refused in `finish` and `withdraw`, both pools (VM).
  - The most recent deposit's coin always holds all the pool owes; I checked the invariant by hand across stray-coin cases. A `finish` or `withdraw` on a stray coin is accepted and harmless: the attacker pays (VM).
- **Token coin.**
  - Exactly one input and one output at the asset's container lock.
  - A deposit adds exactly the denomination.
  - Refused in the VM: a split coin, one unit more or less, the coin one satoshi smaller, the coin drained to a filler beside `finish`, the coin one unit short beside `finish`.
- **State record.** Input index + 1 must be at the record lock with the pool's category; the whole new commitment is pinned. Any changed field, an immutable record, a changed value, or a master commitment is refused (VM, both pools). No immutable NFT a pool can emit parses as state.
- **Merkle updates.** The climb matches Tornado's incremental tree, levels 0–9 in `deposit` and 10–19 in `finish`, bound by `treeState`. `ZEROS` and `EMPTY_ROOT` are the MiMC chain from keccak("tornado") mod r, and the genesis record is exactly the constructor's state (computed).
- **Nullifiers.** 64 levels, empty proof against `nullifierState`, filled root written, `live − 1` must stay ≥ 0. A replay on the next state is refused (VM).
- **Proof binding.** The last input must be at the verifier lock; root, nullifier hash and payee are read at bytes 357–453 of its unlocking; payee = sha256(recipient ‖ 4-byte salt)[0:31] ‖ 00; output 3 (4 for tokens) is pinned to the recipient and the denomination. The verifier fork showed those bytes are necessarily the canonical public inputs the proof was checked over.
- **Third parties.** They can move the satoshi coin and the record back to themselves (documented), run `finish`, and relay a rebuilt withdrawal. They cannot change what any of them pays.

## Shared coins and verifier template

- **MimcHash.**
  - The deployed redeem is `OP_DROP` ‖ artifact bytecode, and its lock is `WORKER_LOCK`.
  - It takes exactly four pushes; the first three are 32 bytes each, so the pool's offsets 1–99 are fixed.
  - Both inputs are checked below r.
  - VM: taken alone at sequence 1440 and version 2; refused at 1439, at version 1, with the lock disabled, with two coins, and with a sweep unlocking inside `finish`.
- **Verifier, against 37c8b9ec.** The only changes are the brand removal, the sweep wrapper in the redeem, and the length constants that follow (recomputed). The sweep needs one input, so it cannot stand in a pool transaction. Role 2 at the last input forces roles 0 and 1 on the two before it. A fourth coin, swapped coins, or an input after them is refused (VM). No aliasing of root, nullifier hash or payee.

## Docs the bytecode contradicts

- `service/verifier/README.md:43-45`: "each pool writes its category into the code … `web/src/verifier.ts` derives a pool's lock". There is no category in the code and one lock for all pools.
- `PRODUCTION.md` "Coins": "Each pool holds 13,000 sat in verifier and hashing coins. Nothing can take them". They are shared, and anyone can sweep one unmoved for 1,440 blocks.
- `scripts/lib/genesis.ts`: "Only the factory's own program can spend a coin at that lock, so the creation is its `new`" and "an event is as good as the factory's own genesis". Finding 1 shows both false.
- `web/src/factory.ts`, `indexer/discover.ts`: "Only the factory's master can mint an NFT of its category; anything else is a stranger's". The creator can mint arbitrary ones at `0x51` and move them.
- `AUDIT.md`: "no record at an event address is taken for an event" holds for pools, not for `PoolCreated`. "which refuses a second pool … on chain" holds for factory state, not for the list.
- `BchPoolDeployer.scash`: "so the `PoolCreated` list names one pool per amount".
- `PRODUCTION.md` table: "no `PoolCreated` or a second one … each refused by the chain" holds only for outputs at the event lock inside the creation.
- `AUDIT.md` / `PRODUCTION.md` malleability lists are incomplete (finding 5). The MimcHash "fourth push" statement is correct.
- `TokenPool.scash` says a deposit coin is "at a P2PKH"; the bytecode tests only a 25-byte lock (the known T9).

## Coverage

- **Fully checked:**
  - BchPool `withdraw` and `finish`, opcode by opcode.
  - MimcHash, and the satoshi-container and record lock templates.
  - The verifier redeem, role dispatch, output rule and public-input parser.
  - `BchPoolDeployer.create`, `TokenPoolDeployer.create`, `Deploy<BchPool>`.
  - The baked tree constants.
- **Partly checked:**
  - BchPool `deposit` and all of TokenPool: read for structure and rules, then confirmed by VM mutations, not every stack shuffle derived.
  - `Deploy<TokenPool>`: its middle section was matched by pattern to the BCH one.
  - The token-container lock: byte-compared and exercised, not read path by path.
  - Verifier roles 0 and 1 layout pins.
- **Not checked:**
  - BCHN itself.
  - The pairing arithmetic and baked verifier constants, byte-identical to 37c8b9ec.
  - Op-cost margins.
  - `delegateArtifact` bytecode in the pool JSONs, which no shipped lock uses.
  - The factories' own genesis.
  - Client code beyond the readers named.
  - The project's suites were not re-run.
